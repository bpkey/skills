# UI and surfaces

Slack's UI is a fixed toolkit. You cannot ship arbitrary HTML or CSS, so design within the toolkit
rather than fighting it — an integration that reads as native beats one that tries to look like your
web app.

## The surfaces

| Surface | What it is | Good for |
|---|---|---|
| Message | A post in a channel or DM, optionally with interactive elements | Notifications, results, approvals, anything tied to a conversation |
| Modal | A stacked dialog opened in response to a user action | Forms, multi-step input, anything needing focus |
| App Home | A per-user tab belonging to your app, with a Messages tab and a configurable Home tab | Dashboards, personal state, settings, an entry point that is not a channel |
| Ephemeral message | A message only one person sees, in place | Errors, confirmations, "only you can see this" replies |
| Canvas | A document surface attached to a channel or standalone | Durable reference content, checklists, notes that outlive the scroll |
| List | A lightweight table inside Slack | Tracking items with fields and status |
| Workflow form | A dialog generated by Workflow Builder | Structured input with zero code |

## Block Kit in one page

Block Kit is Slack's UI framework. You send JSON describing **blocks**, each block may contain
**elements**, and Slack renders them consistently across desktop, mobile, and web. Two things follow
from that design:

- **Layout is Slack's decision, not yours.** You choose blocks and order; you do not control pixels.
- **Interaction is asynchronous.** When someone clicks, Slack sends your app a payload and expects a
  fast acknowledgement. The UI is not a client of your server; it is a message your server answers.

Build layouts in Slack's Block Kit Builder (the interactive playground on `docs.slack.dev`) rather
than by trial and error in code — it renders live and emits the JSON.

## Blocks and elements

**Blocks** are the structural units: a section of text (optionally with an accessory element on the
right), a header, a divider, an image, a context line of small muted text, an actions row holding
several interactive elements, an input row that collects one value, a rich-text block, a video block,
and a file block.

**Elements** are the interactive controls that live inside blocks:

- Buttons, including a button that starts a workflow
- Select menus and multi-select menus, in variants that draw options from your own list, from a remote
  data source, or from Slack's own directories of users, channels, or conversations
- Radio buttons, checkboxes, and an overflow menu
- Date, time, and combined date-time pickers
- Text inputs, including single-line, multi-line, and variants constrained to a number, an email
  address, or a URL
- A rich-text input, which preserves formatting in what the user types
- A file input, for collecting an upload

Element and block availability differs by surface — some inputs only work in modals and App Home, not
in messages. The reference pages for blocks and elements state the compatible surfaces per type;
check there rather than assuming, because this is a common source of an opaque `invalid_blocks` error.

When a payload is rejected, the error rarely says which block is wrong. Bisect by removing blocks, or
paste the payload into Block Kit Builder, which validates precisely.

## Modals

A modal is opened by responding to a user-initiated interaction with a view payload, and it must be
opened promptly — the trigger that authorizes opening it is short-lived, so acknowledge and open
immediately rather than after slow work.

The mechanics worth knowing:

- **Views can be updated or pushed.** Update the current view in place for a step change; push a new
  view for a genuine sub-flow. Deep stacks are unpleasant on mobile — two levels is usually the limit
  of good taste.
- **Submission is a separate event.** On submit you receive all the input values keyed by the block and
  action identifiers you assigned. Choose stable, readable identifiers; parsing this payload is where
  sloppy naming hurts.
- **Validate by responding with errors.** Rather than closing and posting a complaint, return
  field-level errors so Slack shows them inline in the still-open modal.
- **Carry context in private metadata**, not in a global variable. A modal has no session; whatever the
  submission handler needs must travel in the view's own metadata.
- **Do the real work after acknowledging.** Submissions are subject to the same fast-ack rule as
  everything else.

## App Home

App Home gives your app a permanent place in the sidebar with two tabs. The **Messages** tab is a DM
conversation with your app — the natural home for an agent. The **Home** tab is a canvas of blocks you
publish per user, so it can show that person's own state.

Publish the Home tab when the user opens it (there is an event for this) and republish when the
underlying data changes. Treat it as a rendered view of state you already hold, not a place to compute
on demand, because rendering latency is visible.

## Workflow Builder's built-in UI

Without writing code, a workflow can present a **form** and post **messages with buttons**. The form
field types available are single-line and multi-line text, text constrained to an email address or a
URL, whole and decimal numbers with bounds, a single-choice dropdown, a multi-select rendered as a
dropdown or as checkboxes, a yes/no choice as radio buttons, a date picker, a person picker, a channel
picker, a rich-text field, and a file picker. Fields carry a title, a description, a default, and
length limits.

A message step can include buttons that pause the workflow until clicked, and a button can continue
the workflow, start another workflow, or open a link. Combined with branching, that is enough to build
approvals without any hosted code — which is why it is worth checking before building an app.

What Workflow Builder cannot do is arbitrary layout. No side-by-side controls, no overflow menus, no
custom modal you designed. The bridge is a **custom step**: write one piece of code, and it appears in
the visual builder for non-engineers to compose.

## Design guidance that actually matters

- **Lead with the outcome.** The first line of a message should say what happened. People read one line
  in a busy channel.
- **Prefer threads for detail.** Post the summary in channel and the noise in a thread reply.
- **Update instead of repeating.** A single message you rewrite in place beats a stream of near-identical
  posts. This is the most under-used trick on the platform.
- **Make destructive actions confirm.** A button click is one tap on a phone; put anything irreversible
  behind a modal.
- **Write for the person who did not ask.** Channel messages are read by bystanders, so avoid unexplained
  identifiers and internal jargon.
- **Use ephemeral messages for errors** aimed at one person. Do not narrate one user's mistakes to the
  channel.
- **Always set fallback text.** Notifications and unsupported clients show it; a message that arrives as
  a blank push notification is a bug.
- **Respect the theme.** Do not encode colors as meaning without a text label, and remember attachments'
  colored bars are a legacy mechanism.

## Limits

- Up to 50 blocks in a message; up to 100 in a modal or a Home tab.
- Text within blocks has per-field character limits; long content needs truncation with a link out.
- Option lists in select menus are capped, and long lists should use a remote data source instead.
- Modal stacks are limited to a small depth.

Confirm exact numbers on the reference pages before relying on one — treat these as design guidance
rather than as validation rules.
